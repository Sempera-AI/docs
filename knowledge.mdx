A Knowledge Source is a document an Agent can answer from. Sources belong to an agent's library and are grouped into collections; the Agent's draft names which collections are attached.

- `GET /v1/knowledge-sources?agent_id=...` lists sources, one page at a time, beside the agent's `collections` (each with whether it is attached and how it stands against the last build) and `pdf_supported` (whether a PDF upload can be read on this deployment).
- `POST /v1/knowledge-sources?agent_id=...` uploads one document as `multipart/form-data` (`file`, optional `collection`). Plain text, Markdown, CSV, saved web pages, Word documents and PDF are accepted (a PDF is read only where `pdf_supported` is true); the file is read at once and the response (`201`) is the source exactly as a read of it answers. If reading the library back fails after the file is saved, the upload still answers `201`, from the saved record, with `collections` and `attached` `null`; a read of the source a moment later fills them.
- `GET /v1/knowledge-sources/{id}?agent_id=...` reads one source.
- `POST /v1/knowledge-sources/{id}/reparse?agent_id=...` reads the stored file again and answers the `processing` state that re-read left (`parsed`, or `failed` with the reason).
- `DELETE /v1/knowledge-sources/{id}?agent_id=...` removes it from the library; the versions already built with it keep naming it.

A source carries `id`, `name`, `content_type` (the media type of what Sempera read the file as, which can differ from what the uploader claimed), `size_bytes`, `processing` (`state` is `queued`, `parsed` or `failed`, with `error`), `collections` (the ids of this agent's collections that hold it), `attached` (whether one of those collections is attached in the agent's draft) and `added_at` (when the file now on record was uploaded; an in-place edit through `PATCH /v1/knowledge/{id}/content` moves it). An id this agent's library does not hold, another agent's included, is `404 not_found` on every route. A source already removed reads as `404`, but `DELETE` and reparse answer it `409 conflict` with the reason ("that document was already removed"), and a library that cannot be read answers `DELETE` and reparse `409 conflict` with the reason, never `404`.

Processing state is tracked apart from the Agent's configuration: uploading never changes what the Agent says until the collection is attached in the draft and a version is published.

## Collections and agent attachments

Collections belong to an agent's library inside the credential's workspace. They cannot reference another agent's collection or private documents, even when both agents are in the same workspace. These routes require a workspace-bound credential and access to the named agent. Reads need `knowledge:read`; every write needs `knowledge:write` and the owner configure-integration capability. Runtime, CI and read-only keys cannot write. Paused workspaces cannot use the write routes.

- `GET /v1/knowledge-collections?agent_id=...` lists collections, including archived ones, with the usual `limit` and `cursor` pagination.
- `POST /v1/knowledge-collections?agent_id=...` creates a collection (201). Send `name` (nonblank, at most 80 characters), optional `description` (at most 400 characters), and optional `document_ids` (up to 200 library document ids). Omit `document_ids` to start empty. A duplicate active name returns `409 conflict`.
- `POST /v1/knowledge-collections/{collection_id}/documents?agent_id=...` takes `document_ids`, a nonempty array of up to 200 library document ids. It adds them without replacing existing members; repeated ids do not create duplicate memberships. Upload new files through the source upload route above, then pass the returned `id` here. Alternatively, upload with the multipart `collection` field set to the created collection id.
- `GET /v1/agents/{agent_id}/knowledge/collections` returns the effective draft `collection_ids` and its `revision`, including saved attachments when the draft has no attachment edit.
- `PUT /v1/agents/{agent_id}/knowledge/collections/{collection_id}` attaches one collection without dropping the others.
- `DELETE /v1/agents/{agent_id}/knowledge/collections/{collection_id}` detaches one collection without removing its documents or deleting the collection. Both PUT and DELETE take a JSON body with `expect_revision` from the latest attachment read or write. Repeating an attach or detach with the current revision is safe. A stale revision returns `409 conflict` with `reason: stale_draft` and the current `revision`; reload before retrying.

Collection writes return `object: knowledge_collection`, `agent_id`, `id`, `name`, `description`, `documents`, `created_at`, `updated_at` and `archived_at`. Attachment reads and writes return `object: agent_knowledge_collections`, `agent_id`, `collection_ids`, `revision` and `applies_to: next_published_version`. Malformed bodies return `400 validation_failed`. Missing or foreign document and collection ids return `404 not_found`, without disclosing their owner. Removed documents, archived collections and unreadable library indexes return `409 conflict` on collection membership writes. Archived or missing collections already attached can still be detached. Attachment validation retains the agent's existing knowledge and price-policy checks.

For example, using a fictional agent and an already uploaded library document:

```sh
curl -X POST 'https://api.sempera.org/v1/knowledge-collections?agent_id=example-agent' \
  -H "Authorization: Bearer $SEMPERA_API_KEY" -H 'Content-Type: application/json' \
  -d '{"name":"Visitor information"}'

curl -X POST 'https://api.sempera.org/v1/knowledge-collections/col-0123456789ab/documents?agent_id=example-agent' \
  -H "Authorization: Bearer $SEMPERA_API_KEY" -H 'Content-Type: application/json' \
  -d '{"document_ids":["doc-0123456789ab"]}'

curl 'https://api.sempera.org/v1/agents/example-agent/knowledge/collections' \
  -H "Authorization: Bearer $SEMPERA_API_KEY"

curl -X PUT 'https://api.sempera.org/v1/agents/example-agent/knowledge/collections/col-0123456789ab' \
  -H "Authorization: Bearer $SEMPERA_API_KEY" -H 'Content-Type: application/json' \
  -d '{"expect_revision":"REVISION_FROM_READ"}'

curl -X DELETE 'https://api.sempera.org/v1/agents/example-agent/knowledge/collections/col-0123456789ab' \
  -H "Authorization: Bearer $SEMPERA_API_KEY" -H 'Content-Type: application/json' \
  -d '{"expect_revision":"REVISION_FROM_ATTACH"}'
```

Replace the illustrative collection and document ids with the ids returned by creation and upload. The generated TypeScript SDK exposes `createKnowledgeCollection`, `addKnowledgeCollectionDocuments`, `getAgentKnowledgeCollections`, `attachAgentKnowledgeCollection` and `detachAgentKnowledgeCollection`; the Python SDK uses their snake\_case names. Creating, filling, attaching or detaching a collection never publishes an agent or changes an existing built version. Publish separately through the existing review flow before callers use a changed attachment or reading.

## Source testing

`PATCH /v1/knowledge-sources/{id}?agent_id=...` updates a text source with `content` and optional `expect_revision` from the source's `raw.revision`. Stale revisions return `409 conflict` with `current_revision` and do not overwrite the newer reading. Editable kinds are plain text, Markdown, CSV and saved HTML, not Word or PDF. This uses library document ids, not the workspace UUIDs returned by the source testing context.

`POST /v1/knowledge/crawl` takes `agent_id`, `url` and optional `collection` to read one public HTTPS page (201). To refresh, send `agent_id` and `source_id` instead (200). This is a bounded single-page read, not a recursive site crawler. The existing private-address, redirect, size, timeout and quota checks apply. Both operations require `knowledge:write` and the configure-integration role. Neither attaches a source or publishes an agent.

`POST /v1/knowledge/chat` exposes the source-testing contract below to API clients and the console composer. It returns cited retrieved passages, not a generated conversational answer. Each request is independent; it has no hidden conversation history. Model-generated knowledge chat remains outside this contract.

`GET /v1/knowledge/testing-context?agent_id=...` requires `knowledge:read` and the read role capability in the selected workspace. It lists only sources visible to this credential (`sources`: id, name, parse status and owning agent), plus the requested agent's actual pathway nodes (`nodes`: id, label, prompt) and any `node_note`. Nodes are agent configuration: a credential without `agents:read` gets an empty `nodes` list and a note saying why. A foreign agent is not found. Loading a node in the console copies its recorded prompt into the composer; it does not simulate node execution, infer unrecorded per-node source bindings, or change source selection.

`POST /v1/knowledge/test` takes `agent_id`, `question`, and optional `source_ids` (at most 50 canonical source UUIDs from the context response). It requires `knowledge:write`, because a published test adds to the ask log, plus the read role and the same workspace/agent isolation. The question must be nonblank and at most 500 characters. Omitting `source_ids` or setting it to `null` searches the built version; an explicit empty array searches nothing. An explicit selection searches those sources' latest parsed readings, without attaching or publishing them. Foreign or missing sources return 404, malformed ids or invalid questions return 400, and sources that cannot be read or are not ready return 409. Paused workspaces retain the context read but cannot run the POST, following the neighboring action guard and partner entitlement policy.

The result is a deterministic local retrieval diagnostic: question, verdict, reason, scored passages with source attribution, and `mode` (`published` or `selected_sources`). The `published` mode records an ask in the existing knowledge log; a `selected_sources` test records nothing, so it cannot close a caller's open question or change coverage. It is not a model-generated answer or a live call, contacts no provider, and leaves the agent's draft and published artifacts unchanged.

## Console source inventory and query filters

`GET /v1/knowledge/sources` and `/v1/knowledge/sources/picker` accept `agent_id` to narrow the credential's workspace-visible sources. Parsed source inventory rows normally return `COMPLETED`. `STALE` means the owning agent's latest build (its compiled artifact and the verified knowledge snapshot it names) binds an older reading of that document; like `in_version_by` below, this is the latest build on disk, not proof of what is live. An unbuilt or unattached source alone is not evidence of staleness. Failed and processing rows retain `FAILED` and `PROCESSING`. Each row also carries its configured attachment state: `used_by` (`{"agent_id", "shared", "collections": [{"id", "name"}]}` per in-scope agent whose attached collection holds any reading of the source), `agent_count`, `used_by_state` (`complete`, `partial` or `unknown`), `used_by_basis` (`configured`: draft attachment, not the published build), `used_by_incomplete` and `used_by_unreadable` (in-scope agents whose configuration could not be read). `agent_count` is a number only when `used_by_state` is `complete`; otherwise it is null and an empty `used_by` does not mean unattached. `used_by_incomplete` lists the reasons: `unreadable` (an agent's configuration, or the store, could not be read), `outside_scope` (the source's workspace has agents beyond this credential) and `workspace_unknown` (the source is shared but its workspace could not be looked up; no other agent's reference is counted). Beside it, each row reports what agents' LATEST BUILT versions carry: `in_version_by` (same shape as `used_by`, from each in-scope agent's compiled artifact and the knowledge snapshot it names), `in_version_state` (`complete`, `partial` or `unknown`), `in_version_basis` (`latest_build`), `in_version_incomplete` (`unverified_version`, `outside_scope`, `workspace_unknown`, or `unreadable` when unknown) and `in_version_unverified` (every in-scope agent whose artifact or snapshot could not be read or does not match, including former siblings whose share was revoked or who left the workspace, since their last build may still carry the source). Each `used_by` row also carries `in_current_version` (`true`/`false`, or `null` when that agent's build is unverified). `latest_build` is the newest compiled artifact on disk, not proof of what is live: a build may still be going live, and an experiment may serve another saved version. An agent with no build carries nothing; a configuration change reaches `in_version_by` only after the next build. `in_version_state` is `complete` only when no in-scope agent's build is unverified.

`GET /v1/knowledge/queries` supports `source_id`, case-insensitive question search `q`, `status` (`all`, `answered`, `question_answered`, `question_open`), inclusive ISO 8601 `start_date` and `end_date`, `agent_id`, `take` (1 to 100), and `cursor`. These filters apply before pagination. Each row includes workspace-visible canonical `source_ids`; legacy asks without document attribution do not match a source filter. Foreign or missing source filters return 404. A question resolved by a later answer keeps that status even when the answer is outside the requested date window. The console sends local calendar-day boundaries as UTC instants.

The console's Export CSV downloads the currently filtered source inventory, with quoted cells and spreadsheet-formula escaping. Add sources at workspace level chooses the agent that owns the library, then uses the same upload, collection, web-page and Drive workflows as the agent page. Drive authorization and web fetching still require their configured owner permissions and network access; the console never claims a connection or import succeeded without the actual outcome.

## Recorded question lifecycle

`GET /v1/knowledge/queries` includes `question_id`, `question_revision`, `question_state`, `answer` and `answer_source_id`. Question identity is bound to the workspace, agent and normalized question text. Owner annotations are separate from the retrieval diagnostic's `status`; the original query history is retained.

Both mutation routes require `knowledge:write` and the configure-integration role capability. Read-only CI keys and runtime keys cannot use them. Send the recorded `agent_id`, `question` text and current integer `revision` (`question_revision` from the query row, initially 0). A stale revision returns `409 conflict`; an invented question or a question outside the credential's workspace is not found.

- `PATCH /v1/knowledge/questions/{question_id}` takes `action`: `link`, `dismiss` or `delete`. Linking also requires a `source_id` naming a ready source in the workspace and marks the question resolved. Dismiss and delete update only the annotation, not the query history or source library. The response includes `id`, `state`, the new `revision` and `note`.
- `PUT /v1/knowledge/questions/{question_id}/answer` also takes `answer`, a nonblank string of at most 20,000 characters. It ingests the answer as a text source through the ordinary quota and credit checks, then marks the question resolved. The response also includes the canonical `source_id`. A failed ingestion does not resolve the question; retrying the same content reuses its source rather than creating another one.

Neither route changes published knowledge. Attach the source's collection and publish a version before callers can use the answer. Question changes require the workspace database; an unavailable database is not a successful save.

## Retrieval settings

`GET /v1/agents/{agent_id}/knowledge/retrieval-settings` needs `knowledge:read` and answers `{settings, revision, applies_to, note}`. `PUT /v1/agents/{agent_id}/knowledge/retrieval-settings` needs `knowledge:write` and the `owner` role. It takes `settings` and `expect_revision`, the draft revision you read. `settings` is `{boost_columns, exclude_fields}`: up to 50 boost columns with weights from 1 to 20, and up to 50 excluded fields, none of which may also be boosted. Field names are labels in the extracted rows (1 to 64 characters, starting with an ASCII letter, followed by letters, digits, spaces, underscores or hyphens). Names are normalized to lowercase with spaces, underscores and hyphens collapsed to underscores; normalized names must be unique. A stale draft is `409 conflict`.

Save stages the settings in the agent draft, and they apply from the next published version. Exclusions drop labelled fields only, not unlabelled prose, and never delete source data.
