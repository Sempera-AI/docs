`POST /v1/mcp` is a JSON-RPC 2.0 [Model Context Protocol](https://modelcontextprotocol.io) endpoint. A coding agent or assistant can read its workspace and, with the matching permissions, create and edit agents, hold typed test conversations with a draft, see what publishing a draft would change, save versions, publish drafts with an explicit confirmation, run offline tests and simulations, manage text knowledge and bind owned phone numbers. Every tool runs the matching API handler as the caller. The write registry cannot place a call, send an SMS, buy a number or delete a resource. The separately scoped phone tools require the approvals described below. Write access does not bypass roles, workspace boundaries, quotas or release checks.

Use `tools/list` with the credential your client will use to discover the current tools and their input schemas. The result depends on the scopes and permissions of that connection. The tables below describe the tool families.

## Business plan handoff limits

MCP connections, OAuth grants and developer keys cannot open a business plan handoff or approve a purchase. An assistant can help evaluate a draft and point the owner to the App, but it must not ask for card details, confirm a payment, or treat a checkout return as proof of funding or activation. The signed-in workspace owner checks the review and any billing status in the App. Purchase consent is separate from permission to contact a business.

## Connect

Use the same bearer key as every other route ([Authentication and credentials](/authentication)), or sign in with OAuth (below). A key needs `agents:read` or a phone scope to connect. An OAuth token can connect with any approved scope. `tools/list` shows the tools that the credential can use. CI keys are refused with `403 forbidden`. The call below asks for the setup snippet of one client. The same answer is available at `GET /v1/mcp/clients/{client}`.

```bash
curl -X POST https://api.sempera.org/v1/mcp \
  -H "Authorization: Bearer sempera_sk_..." \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"mcp_client_setup","arguments":{"client":"claude-code"}}}'
```

The endpoint takes one JSON message per POST and answers one JSON body. It offers no event stream and no session: with a live credential, any method but `POST` (`GET`, `HEAD` and `DELETE` among them) answers `405` with `Allow: POST`, and it sends no `Mcp-Session-Id`. That is the plain JSON form of the Streamable HTTP transport, which every published MCP revision lets a server choose and requires a client to accept, so ChatGPT and Claude need no event stream to connect. No tool here sends progress, so none is offered.

## Sign in with OAuth

A host that cannot hold a static key (ChatGPT, Claude) signs in with OAuth 2.1 instead. Give it the URL `https://api.sempera.org/v1/mcp`. Bearer keys keep working exactly as before.

1. The host posts without a token and gets `401` with `WWW-Authenticate: Bearer resource_metadata="https://api.sempera.org/.well-known/oauth-protected-resource/v1/mcp"`.
2. It reads that document, then `https://api.sempera.org/.well-known/oauth-authorization-server`.
3. It registers itself at `POST /v1/oauth/register` (RFC 7591) and sends the browser to `GET /v1/oauth/authorize` with PKCE (`S256`, required), the `resource` `https://api.sempera.org/v1/mcp`, and the scopes it wants. Redirects match exactly. A loopback address may differ by port alone, because a native client binds a free port each time.
4. The person signs in on `app.sempera.org` if they have not, and a workspace owner approves on the consent page: which client, which workspace, which scopes, and where the answer goes. A client Sempera cannot recognise by its published redirect is shown as unverified. The owner can approve fewer scopes than were asked for, never more.
5. The host swaps the code at `POST /v1/oauth/token`. An access token lasts one hour and a refresh token 30 days. Each refresh turns the refresh token over. Presenting a spent one ends every token from that sign-in, and so does presenting a spent code.

| Scope | What it allows |
| --- | --- |
| `phone:read` | See the line, plan state and allowance, and read call tasks/results |
| `phone:call` | Preview calls, start approved calls and cancel tasks |
| `phone:text` | Preview texts, send approved texts and read their threads |
| `phone:approve` | Lets the signed-in owner approve a previewed call or text from its card in the chat. Off on the consent screen until the owner turns it on, and off on Sempera's side until enabled for that chat app |

Owners can also approve management permissions for reading workspace data, creating and editing agent drafts, publishing, rolling back, and attaching existing numbers. The consent screen shows the permissions the client requests and lets the owner narrow them. `create_agent` creates an unpublished draft. An OAuth connection needs both edit and publish consent to run `save_agent_version`, because the build becomes the current version. Call transcripts and recording links require a separate opt-in that starts off. When the token also holds the relevant read scope, `get_call_log` and `get_session` include available transcript excerpts and a link to available playback in the signed-in App. Lists remain metadata-only.

In-chat approval (`phone:approve`) is the one way an OAuth client can carry an owner's approval, and it is built for the card, not the assistant. The preview card receives a single-use code in the tool result's `_meta`, never in `content` or `structuredContent`, bound to that request, the consenting owner, that connection and an expiry of at most ten minutes. The card sends it to `phone_approve_request`, a tool marked for the card alone (`_meta.ui.visibility: ["app"]`). Sempera then repeats every check a start makes, allows one approval per request and a daily number of in-chat approvals, records the approval in the workspace's activity record and emails the owner. The card always keeps the **Approve in the Sempera app** link. What Sempera cannot check: a card and the assistant call with the same token, so keeping that tool and that code away from the model is the chat app's job. In-chat approval is turned on only for a chat app where that has been confirmed.

OAuth grants exclude purchases, billing changes, member and API-key management, paid tests and knowledge-source writes. A request with an unsupported scope is refused with `invalid_scope`. A client that requests no scopes gets `phone:read`.

A token works on `POST /v1/mcp` and nowhere else (any other route answers `401`), and only for the resource it was issued to. It resolves to the same principal a key does, so the same role, scope, workspace and audit checks apply. Only `SHA-256` hashes of tokens, codes and client secrets are stored.

Client Metadata Documents are not offered. A host that prefers them falls back to registration, which ChatGPT, Claude and Codex all document. Tools do not yet ask for more scope mid-conversation: to change what a client holds, approve it again, which replaces its grant.

Owners see every client in Settings, Connected clients (`GET /v1/client-grants`), with its scopes and last use, and end one with `DELETE /v1/client-grants/{grant_id}`. Its tokens stop at once and every other client keeps working.

Public discovery is served by `GET /.well-known/oauth-authorization-server`, `GET /.well-known/oauth-protected-resource` and `GET /.well-known/oauth-protected-resource/v1/mcp`. These publish authorization-server and resource metadata, without granting access or replacing owner consent.

## Protocol versions

Two revisions are spoken. Which rules a request is held to depends on one thing: whether it carries the `MCP-Protocol-Version` header.

| A request that... | What it gets |
| --- | --- |
| carries `MCP-Protocol-Version: 2025-06-18` or `MCP-Protocol-Version: 2024-11-05` | The Streamable HTTP rules for a server with no stream and no sessions. A notification, or a client's answer to a request, is accepted with `202` and no body. A body without `jsonrpc: "2.0"`, a request without an `id`, or a JSON array is refused with `400`. The two headers are served identically; what `initialize` answers depends only on the revision named in its own parameters. |
| carries `MCP-Protocol-Version` naming any other revision, empty or not | `400 validation_failed`, with the revisions spoken listed in `supported`. Before the endpoint negotiated, the header was ignored. |
| carries no `MCP-Protocol-Version` header | Served as this endpoint always served it: a notification gets `200` and an empty result, and a JSON array is a `400`. Only four of its answers change; they are listed under Which clients move. |

`initialize` answers the revision the client asked for when it is `2025-06-18` or `2024-11-05`. For a newer date (`2025-11-25`, `2026-07-28` and later) it answers `2025-06-18`, the newest spoken; for `2025-03-26`, an older date, an unknown value or none it answers `2024-11-05`, which is all it answered before it negotiated. Prompts, completions, logging, event streams and sessions are not offered; nothing here claims them. Resources are offered only as the in-chat screens described under Screens, and `structuredContent` only on the two tools those screens belong to, without an `outputSchema`.

Neither supported revision includes an `instructions` field in `initialize`. The editing and testing contracts are documented under Draft and test over MCP and Test an agent from your assistant.

With either supported version header, an `id` must be a string or a finite integral number. Numeric spellings such as `1`, `1.0` and `1e0` are accepted and the parsed value is echoed without conversion. Null, booleans, objects, arrays, fractional numbers and non-finite values are refused before a tool is called, with HTTP `400`, JSON-RPC `-32600` and a null response id. Notifications still omit the id and receive `202` with no body; valid client replies receive the same empty acknowledgement. Requests without the version header retain their legacy behavior.

### Which clients move

- **A client that sends the header.** The revisions from `2025-06-18` on require a client to send `MCP-Protocol-Version` on every request after `initialize`, so a client built on a current SDK sends it. Such a client now negotiates `2025-06-18` (it asks for a newer revision and is answered with the newest spoken), then gets `202` for its `notifications/initialized`, and may try to open a stream with a `GET` on the endpoint and be answered `405`, which that revision allows for a server that offers none. This is a change from the endpoint before this release, which answered such a client `2024-11-05` and `200`. A client that sends a header naming any other revision is refused with `400`.
- **A client that sends no header on any request.** Four of the answers it already got change: `initialize` asking for `2025-06-18` or newer is answered `2025-06-18` (it was `2024-11-05`); `tools/list` with a `cursor` is a `-32602` error (it was ignored, and the list never paged); each of the three original tools gains `title`, `annotations` and `_meta` in `tools/list`; and `initialize` declares `resources`, so `resources/list` answers the screens of the tools it can call (it was `-32601`). Its `tools/list` also includes the read tools its scopes allow. Every other answer to it is unchanged, including the text of the original tools' results and their `-32000` errors; a result now also carries `usage` beside `content` (see Usage on every result).
- **A browser page on another site.** See the `Origin` rule below. The API answers a browser's preflight for this endpoint with `401` and no CORS headers, so such a page could not send it a JSON request with a key in the first place; the `Origin` rule is a second lock.

## Origin

Every request that carries an `Origin` header is checked, with or without `MCP-Protocol-Version` (the only method served is `POST`; any other is refused `405`, or `401` with no live credential, before it gets that far). The `Origin` value must be this deployment's own host, a host the deployment is configured to allow, or an origin the App is served from (the origins the deployment lists for its web App); otherwise the answer is `403 forbidden`, and the request's scope, version header and body are never looked at. The App's own pages therefore reach this endpoint through the App's proxy even when that proxy runs on another host or port than the API, as it does in development and in the browser tests.

The API's front door looks at the credential first: a request with no key, an unknown key or a revoked key is refused `401` whatever its `Origin`, as is a dead token, and that `401` says where to sign in, so the `403` is what a request with a live key and a foreign `Origin` gets. A request with no `Origin` header (a command-line tool, an SDK, a server-side client) is not a browser's and is not checked. `Origin: null`, an empty `Origin` and a value that is not a URL are foreign, and so is a request with several `Origin` headers when any one of them is. The deployment's own host means the host and port the request arrived with, so that half relies on the deployment's host policy (which answers `404` to a host it does not know) and does not compare the scheme; an App origin is compared whole, scheme, host and port. This rule is new with the release that added these tools: a client that sent an `Origin` of another site and was served before is refused now.

## Arguments, answers and errors

- An agent is named `agent_id` in every tool, whichever path variable the route calls it. Ids are letters, digits, `.`, `_`, `:` and `-`, up to 200 characters. An unknown argument, a missing required one, a wrong type or an out-of-range number is refused before anything is read, with the argument named.
- An answer is the route's JSON as text in one `text` content item (narrowed as a later section says for seventeen tools), or, for the two guide tools, its Markdown. A failure is a tool result with `isError: true` whose text is the route's own error envelope, for example `{"error":{"code":"not_found","message":"no such agent","request_id":"req_..."}}`. The codes are those in [Errors and limits](/errors-and-limits), and `request_id` is the one the call returned in `X-Request-Id`. An answer about your workspace never carries an internal address, the name of a setting, a file path, a stack trace or the name of an engine or supplier behind Sempera; the tests scan every tool's answer for them.
- Arguments that are not a JSON object, an unknown method and an unknown cursor on `tools/list` are protocol errors (`-32602`, `-32601`). The three original tools keep reporting a refusal as JSON-RPC error `-32000`, as they always did; every newer tool reports it as a tool result.
- Lists page with `limit` (1 to 200, default 50; `list_agent_check_runs` takes 1 to 100) and `cursor`. Pass `next_cursor` from the last page back unchanged to read the next one (`nextCursor` on `list_tools`, `data.next_cursor` on `list_eval_agents`). A cursor is an opaque position: the same cursor gives the same page while the rows are unchanged, and one issued to another key reads only that key's own rows. `list_integrations`, `list_voices` and the environment, branch and deployment reads answer in one piece.
- An answer larger than 1 MiB is refused with `payload_too_large`; ask for a smaller page or a more specific id. A read that runs longer than 30 seconds is refused with `service_unavailable`. A call counts once against the key's request budget ([Errors and limits](/errors-and-limits)), like any other request.
- A secret environment variable always reads `null` in `list_agent_variables`; its value never leaves the server.

### What seventeen tools leave out

Seventeen tools answer a short, written-out list of fields rather than the route's whole answer. A field the route gains later is not passed on until this page and the tool both name it.

- **Calls and conversation records** (`list_calls`, `get_call_log`, `list_sessions`, `get_session`) include the id, agent, channel, status, start and end times, duration, language, outcome code and label, version and turn count. There is no transcript or recording link without the separate OAuth content consent, and lists always return metadata only. Caller numbers, summaries, titles, extracted values and provider logs are omitted. Outcome, language and version are shown only when they have the shape of a short code (letters, digits and `.` `_` `:` `-`, with no spaces). Otherwise they read `null`. An outcome label is shown only when it is a Sempera outcome label or the plain wording of its code. No tool argument changes the consent required for content. `get_call_transcript` uses its own transcript permission.
- \*\*`list_post_call_events`\*\* returns each ended phone call as a `call.completed` event: the event id, `created_at` (when the call's record was stored), and in `data` the call id, agent, start time, duration, outcome code and `recording_stored`. The outcome reads `null` unless it has the shape of a short code. No caller number, summary, recording link or transcript.
- \*\*`get_eval_results`\*\* returns counts, pass rates, the weekly and per-version trend, and one row per scored conversation with its verdict and score. It leaves out the judge's reasoning (which quotes the conversation), the failure clusters built from it, the judge's rubric and the evaluator's own configuration.
- \*\*`list_voices`\*\* takes no arguments. It lists the built-in voices an agent may name, with each one's language and whether it may carry a live call, followed by your workspace's own ready custom voices. It asks no outside voice library and takes no search, language or provider filter. No other workspace's voice is ever listed.
- \*\*`list_tests` and `get_test_run`\*\* read legacy battery jobs in memory (at most 20 newest), plus candidate checks retained in the App's canonical Checks ledger on Sempera's servers. A retained candidate is resolved by id only among the caller's authorized agents after restart. Legacy jobs are lost at restart. A run shows its state and outcome, not the failure text of a run that crashed nor who started it. Another workspace's run is answered `not found` with the same sentence as an unknown id.
- \*\*`list_agent_check_runs`\*\* returns each check run's id, agent, version, status and times. A run that ended in an error keeps the status `ERROR`, and its `error_message` is always the one sentence "The run ended in an error. Its detail is not returned over MCP." in place of the system's own words for what went wrong, which can name a file on a server, a setting or an address.

- \*\*`list_webhooks` and `get_webhook`\*\* show the endpoint id, agent binding, enabled state, event names and timestamps. `url_host` is only the receiving host; it omits the scheme, port, path, query and fragment. `has_secret` and `has_post_call_filter` say whether those are set, but the signing secret, filter body and owner-written description are never returned. Find post-call notifications by looking for `call.completed` in `events`. Omit `agent_id` to see all workspace endpoints, or pass it to list only endpoints bound to that agent (the REST query parameter is `agent`).
- \*\*`get_call_transcript`\*\* returns what the caller and the agent said, line by line (`turns`, each with `index`, `caller`, `agent` and `input: keypad` when the caller pressed keys), and nothing else of the call record: no caller number, summary, recording, captured values or prompts. A line longer than 4000 characters is cut and marked `truncated`, and at most 500 turns are returned (`turns_cut` says when there were more). The answer carries `untrusted: true`: it is what people said on the phone, not instructions.
- \*\*`list_phone_numbers`\*\* returns each number bound to the agent, when it was bound or released and whether it is shared as an outbound caller id. The carrier's readback is not returned.
- \*\*`list_alerts`\*\* returns each alert rule's metric, thresholds, the agents it covers, whether it is on and whether it is firing, and `notification_count`. Where its notifications go (addresses, channels, receiving URLs) is not returned.
- \*\*`list_members`\*\* returns each active member's user id, first and last name, role, whether they own the workspace and when they joined. No email address and no phone number.
- \*\*`list_webhook_deliveries`\*\* shows recorded attempts, newest first: the event id and type, attempt number, status, HTTP response code and timestamps. It does not show the delivery payload or receiver error text, and it does not contact the receiver. A 2xx response shows the receiver accepted the request, not that it processed the notification.

An outside client needs an API key with both `agents:read` and `webhooks:read` to use these tools. The Connected AI client presets and OAuth phone grants do not include `webhooks:read`.

Previews place no call, send no text and reserve no spend, but they store a new task or message for owner approval. They are therefore not read-only or idempotent; repeating a preview creates another record. They are non-destructive and closed-world. Starting a call or sending a text is not read-only, is open-world and is marked destructive because a call or delivered message cannot be taken back. Cancelling is destructive and open-world because it can end a live call without a way to resume it. It does not delete the task record. Start, send and cancel are idempotent for the same approval or task id. Phone reads have no call, message or approval side effects; they record credential usage.

They run the same operations as the [phone REST routes](/phone-plan#a-call) and refuse with the same codes. An ordinary workspace API key cannot use them: connect the client with OAuth, a phone-enabled MCP key or a scoped REST credential. OAuth tokens and MCP keys work on MCP only; a scoped REST credential also works on the phone REST routes.

In Settings \> Connected clients \> **Connected AI clients**, choose **Read**, turn on **Phone tools (owner approval required)** and create a new connection. This adds all three phone scopes to the read scopes; it does not upgrade an old key or create a phone-only credential. For OAuth, the host must request `phone:read` and `phone:call` for the call journey; approve `phone:text` only if needed.

A preview returns `approval.url` for the signed-in owner unless standing approval covers it. Unless the preview returned `standing: true`, read the task until `approved` is true. Then start the unchanged request with the preview's `id` and `spend_bound_cents`. `reserved` means queued, not dialing. Poll the task for its recorded outcome; a finished call does not reopen the assistant chat. No tool approves, buys, subscribes or tops up. Follow [Your first call](/phone-plan#your-first-call) for setup, limits and refusal help. Public purchase and a complete assistant-to-handset journey are not yet verified as available.

Three tools act on what is already running. Each runs existing routes as the caller, with the route's own scope, role, workspace and agent checks, and is listed only to a credential that holds its scope.

| --- | --- | --- | --- | --- |
| `get_call_recording` | `GET /v1/calls/{call_id}`, then `GET /v1/recordings/{recording_id}` | `calls:read` | call\_id (required), agent\_id | No |
| `rollback_agent` | `POST /v1/agents/{agent_id}/rollback` (owner role) | `agents:publish` | agent\_id, to\_deployment\_id, version\_number, confirm (the agent\_id again), idempotency\_key (required) | Yes |

- `get_call_recording` reads the call for its stored recording and then asks for a signed link, which expires after five minutes and is recorded in the workspace's audit log. A call that was not recorded, or whose recording was not kept, is refused `not_found` and nothing is signed. The link is bound to the credential that asked; the audio itself is served only to a signed-in member of the workspace in the App ([Call recordings](/recordings)), so a link issued to an API key or an OAuth token does not play. The answer is the rollback record and whether the platform read back the restored version (`verified`).
- `stop_call` ends one active phone call on an agent's line. The caller is disconnected and the call cannot be resumed, so it is marked destructive and open-world. It places no call. `calls:write` is not on any Connected AI client preset or OAuth grant, so only an API key that holds it lists this tool.
- Both writes take `idempotency_key`, write one `mcp.tool_call` audit row per call and one usage row under `mcp:<tool>` per completed call, as the draft tools do.

## Not available over MCP

There is no `/v1` route for buying a number, inviting a member or changing billing. Outbound calls are available only through the separately scoped and approved phone tools described above. The write registry is an explicit list, not arbitrary HTTP access.
- The caller's number and a call's summary. What was said is `get_call_transcript`, behind its own transcript permission.
- Integration detail by key. `list_integrations` answers; there is no tool for one integration.
- Creating, editing, testing or resending webhooks, a pushed post-call event subscription over MCP (Sempera does not call your assistant; read `list_post_call_events` instead, see below), MCP prompts, and any resource other than the screens. The webhook tools only inspect existing endpoints and recorded attempts.

## Post-call notifications over MCP

An assistant learns about finished calls by asking, not by being called. The hosted server opens no event stream and keeps no callback for your assistant: pushed MCP event subscriptions are not switched on, because they still need a release, an owner grant and a durable delivery lifecycle. `list_post_call_events` (`GET /v1/post-call-events`, `calls:read`) is the pull side of the `call.completed` webhook.

- It lists the phone calls of one agent that ended, oldest first, in the order their records were stored. They are the same calls, with the same ids, that `list_calls` and `GET /v1/calls` list; read one with `get_call_log`.
- The answer carries `next_after`. Send it back unchanged as `after` and you get only the calls that ended since. It is returned even when nothing new has ended, so an assistant keeps one value and asks again later. Without `after` the read starts at the oldest retained call. `has_more: true` means more are waiting now.
- An event's `id` is derived from its call, so reading the same calls twice names the same events, and an assistant that lost its place can drop the ones it has seen.
- A call deleted under retention, or recorded with Exclude from history, is not listed. A call from another workspace's agent is refused like an unknown agent.
- An `after` this route did not issue is refused `validation_failed` with `field: after`.

To have Sempera push each finished call to a server you run, create a webhook endpoint for `call.completed` in the App or with `POST /v1/webhooks`; that is unchanged and not available over MCP.

## Draft and test over MCP

Four tools run the same write routes the App and REST clients use, as the caller, with the route's own scope, role, workspace and agent checks. A draft edited here is the one canonical draft the App opens; there is no second copy. They are listed in `tools/list` only to a credential that holds their scope.

| Tool | Runs | Scope | Arguments | Changes anything? |
| --- | --- | --- | --- | --- |
| `create_agent` | `POST /v1/agents` (owner role) | `agents:write` | name (required), template, idempotency\_key (required) | Yes |
| `update_agent_draft` | `PATCH /v1/agents/{agent_id}/draft` | `agents:write` | agent\_id (required), fields (required), expect\_revision (required), idempotency\_key (required) | Yes |
| `run_agent_tests` | `POST /v1/tests` | `tests:write` | agent\_id (required), scenarios, candidate\_revision, runtime\_policy, idempotency\_key (required) | Yes |
| `run_agent_conversation` | `POST /v1/agents/{agent_id}/preview`, once per message | `agents:write` and `tests:write` | agent\_id (required), messages (required, 1 to 10), version (`draft` or `published`, default `draft`), idempotency\_key (required) | Yes |

- `idempotency_key` is the request's identity: a retry with the same value gets the first answer back and changes nothing again; the same value with a different change is refused `idempotency_key_reused`.
- `update_agent_draft` needs `expect_revision`, the `revision` that `get_agent_draft` returned. An edit made from an older read is refused `conflict` with `reason: stale_draft`, so a newer change by someone else is never overwritten. The keys `fields` may carry are listed in the draft's `editable_fields`; the common ones are `system_prompt` (standing instructions), `greeting` (the first sentence), `voice` (an id from `list_voices`), `request_data` (facts the agent knows on every call, a list of `key` and `value` rows) and `knowledge_collections`.
- `update_agent_draft` checks every supplied field against the editing contract before the draft route runs, with no model call: a key the editor cannot change, or a value of the wrong shape, is refused `validation_failed` with `error.errors`, one `{field, message}` row per failing field (all of them at once), `error.field` naming the first, and `error.model_calls: 0`. What a value means is still checked when the draft is saved and at publish.
- `get_agent_authoring_context` is the one read a connected assistant needs to write or review an agent itself: the instructions (the draft's when it edited them, else the current document, invisible section markers included: keep them when writing the document back), the other draft fields, warnings, `contract` (`editable_fields` and the `expect_revision` to send), `knowledge` (up to 50 sources) and `checks` (up to 50 scenarios). A section this credential cannot read answers `{"unavailable": <code>}`. Sempera runs no model for it, and its usage row records zero tokens.
- `run_agent_tests` with `candidate_revision` and `runtime_policy` runs the reviewed draft through the App's canonical Checks runner, never a real call, booking, SMS or email. Without both it retains the legacy battery behavior, but a paid or unknown configured runtime is refused. Read the run with `get_test_run`.
- `run_agent_conversation` types each message to the agent in order, on one typed preview session, and answers the transcript: `transcript` holds one row per line (`caller` and `agent` with their `text`, and `tool` with only the `name` of a tool the agent reached for), plus `session_id`, `turns` and `ended`. It is the App's typed preview: never a phone call, every tool answers from its test fixture, and each message counts against the workspace's typed test allowance. A retry with the same `idempotency_key` replays the turns already taken instead of typing them again. If a message is refused, the answer is that refusal with `turns_taken`, the number of messages answered before it. It needs `tests:write` as well as `agents:write`, so a connection granted drafting alone, or testing alone, does not hold it.
- Every call writes one row to the workspace's audit log (`mcp.tool_call`: the tool, the agent, the outcome, the credential id; never the text you sent) and each completed change one builder usage row under `mcp:<tool>` (a refused call or a replayed retry is not counted), apart from the call minutes the call service records.

## Test an agent from your assistant

Your assistant can test an agent turn by turn and grade the result itself. It plays the caller; Sempera runs only the agent. Two tools do this, and neither places a phone call.

| Tool | Runs | Scope | Arguments | Changes anything? |
| --- | --- | --- | --- | --- |
| `test_agent_turn` | One typed turn of the agent, on Sempera's model | `agents:write` and `tests:write` | agent\_id (required), caller\_message (required), history, version (`draft` or `published`, default `draft`) | Yes |
| `judge_test_locally` | The reads `get_agent_authoring_context` uses; no model | `agents:read` | agent\_id (required) | No |

`test_agent_turn` is the one tool on this page built to spend Sempera's model budget on purpose: the agent has to answer as itself, so its side of the turn runs on Sempera's model. Each call is one agent turn, counts one message against the workspace's daily typed test allowance (the same allowance the App's Test and `run_agent_conversation` use), and reports what it used in `usage`. Your assistant's own thinking (writing the caller's lines, grading) costs Sempera nothing.

- **It keeps nothing between calls.** There is no session id. Send the turns so far as `history`, a list of `{"role": "caller" | "agent", "text": "..."}` rows, oldest first, with your next `caller_message`. The answer's `history` is the whole conversation after the turn: pass it back unchanged next time. The prior turns are put in front of the agent as words already said; Sempera runs no model to load them.
- **Limits.** A conversation holds at most 10 caller messages (the one you send counted), so `history` holds at most 19 rows, and each line is at most 4000 characters. More than that is refused `validation_failed` naming the argument, and nothing is run or counted. Start a new conversation instead.
- **The answer.** `reply` (what the agent said), `tool_calls` (each tool the agent reached for: its `name`, the `arguments` the typed preview records for it, its `environment` and a one-sentence `result`), `ended` (the agent finished the call), `history` and `usage`.
- **Nothing real happens.** Every tool answers from its test fixture, on the published version too, so nothing is booked, sent or changed. No conversation record is written.
- **What a replay cannot restore.** The agent starts each call from its first step with the history in front of it. Where it stood in a multi-step flow, and the values it had collected, are not carried over from the earlier calls: it works them out again from the history. For a test that depends on exact step-by-step state, use `run_agent_conversation`, which holds one session for up to ten messages.
- **On a draft, each call compiles the draft again**, so it also counts against the daily limit on tests of unpublished changes. Test the published version (`"version": "published"`) when you are not testing an edit.
- **Refusals.** A reached allowance is `rate_limited` with `retry_after_s` and the sentence a person reads. An agent in another workspace is `not_found`, the same as an id that does not exist. A credential without both scopes is `insufficient_scope`.

`judge_test_locally` returns a rubric and runs no model: `checks` (the agent's test scenarios, each with `when`, `until` and `steps`), `success_criteria` (what each check says must hold, one row each), `conduct_rules` (four fixed rules, the agent's own instructions and its greeting), `how_to_grade` and `answer_format`. Your assistant reads the transcript against it and gives a verdict per item: `pass`, `fail` or `not_tested`. A check the conversation never reached is `not_tested`, not passed. A section this credential cannot read answers `{"unavailable": <code>}`.

```bash
  -H "Authorization: Bearer sempera_sk_..." \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"test_agent_turn","arguments":{"agent_id":"northwind-barbers","history":[{"role":"caller","text":"Hi, can I book a haircut for Friday?"},{"role":"agent","text":"Hello, this is the assistant at Northwind Barbers. Friday works. Would 10:00 or 14:30 suit you?"}],"caller_message":"14:30 please. My name is Alex."}}}'
```

When the conversation is done, read the rubric and grade the transcript yourself:

```bash
curl -X POST https://api.sempera.org/v1/mcp \
  -H "Authorization: Bearer sempera_sk_..." \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"judge_test_locally","arguments":{"agent_id":"northwind-barbers"}}}'
```

A verdict your assistant might then write: "Books a haircut: pass (the agent offered two times and confirmed 14:30). Conduct: pass. Reschedules a booking: not\_tested."

### Usage on every result

A tool result that involved no Sempera model call says so beside its `content`: `"usage": {"sempera_model_calls": 0}`. Every read carries it (the original three tools, the read tools, the follow-up reads, `get_agent_authoring_context`, `judge_test_locally`, the phone reads), and so does `update_agent_draft`, whose pre-check and save run no model. A refusal of one of those carries it too.

`test_agent_turn` reports its real numbers there and in its answer: `sempera_model_calls` (at most one, including retries and tool follow-ups), `input_tokens`, `output_tokens`, `total_tokens` and `tokens_reported`. Tokens the model did not report read `null` with `tokens_reported: false`; they are never estimated in the answer. Refusals before the agent runs report zero, and failures after a request retain its count. If a tool answer or a rejected draft would need another model request, it is stopped: `reply` is empty and `note` explains that no reply was completed. Do not grade an incomplete turn as a pass.

Model-free writes also carry zero: `create_agent`, the version, knowledge and number writes, and every phone operation. That describes model use during the tool request only, not a claim that those operations have no other cost or that a queued phone call will use no model later. `run_agent_conversation`, `run_agent_tests` and `run_agent_simulations` are not counted per result here and do not claim zero.

## Connected AI clients

An owner connects one outside client at a time in Settings \> Connected clients \> Connected AI clients (or `POST /v1/mcp/connections` with `client`, `access` and optional `call_records`, `phone` and `expires_in_days`). Each connection is its own key, shown once, that:

- works on `POST /v1/mcp` and nothing else (any other route answers `403 forbidden`);
- holds a fixed scope list: `read` gives the preset read scopes (call and conversation metadata only with `call_records`), `draft` adds only `agents:write`, `test` adds only `tests:write`, and `build` adds both. Owners can authorize drafting without test execution, or testing without draft edits. Explicit `write` access also adds `agents:publish`, `knowledge:write`, `phone_numbers:read` and `phone_numbers:write`. It never holds `calls:write` or a key scope. Existing keys are not upgraded;
- expires (90 days by default, at most 365) and is listed with when it was last used.

`GET /v1/mcp/connections` lists them and `DELETE /v1/mcp/connections/{connection_id}` disconnects one. Disconnecting revokes that key only: the deployed agents keep answering calls exactly as before. Another workspace's connection, and an ordinary API key, read as `not_found` on these routes.

## Write tools and a safe agent recipe

Choose Write in Settings \> Connected clients \> Connected AI clients and confirm the permission change. This creates a new expiring key, not an upgrade of an existing connection. Ordinary API keys can use these tools when their scopes and roles allow them. A client should ask its operator to approve publishing and number binding before invoking those tools.

Every write requires `idempotency_key`. Reuse it only for an identical retry. A timeout is not proof that nothing changed: retry with the same key and read the resource before attempting another change.

| Tool | Method and path | Scope | Arguments besides idempotency\_key | Changes anything? |
| --- | --- | --- | --- | --- |
| `save_agent_version` | `POST /v1/agents/{agent_id}/versions` | `agents:write` | agent\_id | Yes |
| `publish_agent_version` | `POST /v1/agents/{agent_id}/publish` | `agents:publish` | agent\_id, reason, confirm (the agent\_id again); optional expect\_revision | Yes |
| `run_agent_simulations` | `POST /v1/agents/{agent_id}/simulations` | `tests:write` | agent\_id, scenario\_keys, optional repeats | Yes |
| `bind_phone_number` | `POST /v1/phone-numbers` | `phone_numbers:write` | agent\_id, number | Yes |
| `create_knowledge_source` | `POST /v1/knowledge-sources/text` | `knowledge:write` | agent\_id, name ending in .txt, content | Yes |
| `update_knowledge_content` | `PATCH /v1/knowledge/{uuid}/content` | `knowledge:write` | source\_id, content, expect\_version\_id | Yes |
| `reparse_knowledge_source` | `POST /v1/knowledge-sources/{source_id}/reparse` | `knowledge:write` | agent\_id, source\_id | Yes |

| Tool | Reads | Scope | Arguments | Changes anything? |
| --- | --- | --- | --- | --- |
| `get_knowledge_content` | `GET /v1/knowledge/{uuid}/content` | `knowledge:read` | source\_id (required) | No |
| `get_agent_simulation` | `GET /v1/agents/{agent_id}/simulations/{simulation_id}` | `tests:read` | agent\_id (required), simulation\_id (required) | No |
| `get_agent_draft_changes` | `GET /v1/agents/{agent_id}/draft` | `agents:read` | agent\_id (required) | No |
| `get_agent_authoring_context` | `GET /v1/agents/{agent_id}/draft`, `GET /v1/agents/{agent_id}`, `GET /v1/knowledge-sources`, `GET /v2/agents/{uuid}/scenarios` | `agents:read` | agent\_id (required) | No |

Follow-up reads are `get_knowledge_content` (`source_id`, `knowledge:read`, `GET /v1/knowledge/{uuid}/content`), `get_agent_simulation` (`agent_id`, `simulation_id`, `tests:read`, `GET /v1/agents/{agent_id}/simulations/{simulation_id}`) and `get_agent_draft_changes` (`agent_id`, `agents:read`, `GET /v1/agents/{agent_id}/draft`). For `get_knowledge_content`, pass the library `id` from `list_knowledge_sources` or `get_knowledge_source`, or pass the `content_id` from `create_knowledge_source`. If no text is stored, the tool returns `data.content: null` and an explanation. To edit text, use the `content_id` and pass the `data.version_id` that you read as `expect_version_id`. A stale edit is refused.

`get_agent_draft_changes` compares the draft with the published version, using the same list the App's publish confirmation shows: `changes` has one row per setting that would change (`key`, `label`, `risk`, `before`, `after`, and `truncated` when a value was shortened to fit), `blocking` lists anything that would refuse the publish, and `ready_to_publish` is true only when something would change and nothing blocks it. It also returns the draft's `revision` and `risk_max`. A draft whose highest risk is `HIGH` needs the full name of the person deciding, which `publish_agent_version` does not take, so the tool refuses it with `conflict` and a person publishes it from the App.

`publish_agent_version` publishes only when `confirm` repeats the `agent_id`. A call without it, or with any other value, is refused `validation_failed` naming `confirm`, and nothing is published. A credential without `agents:publish` is refused `insufficient_scope` before its arguments are read.

1. Connect with the narrowest access needed and call `tools/list` to discover available tools.
2. Use `create_agent` with a synthetic business name, then `get_agent_draft` and `update_agent_draft` with the returned revision. The App reads the same draft.
3. Add a text source with `create_knowledge_source`. Use the draft's editable attachment fields to attach its collection. Uploading alone does not attach it or change the live agent.
4. Try the draft with `run_agent_conversation` and read its transcript, then run `run_agent_tests` on the draft and read `get_test_run`. A failed or unavailable runner is not a passed test.
5. Read `get_agent_draft_changes` and show the operator what would change. With their explicit approval, use `publish_agent_version` with `confirm` set to the agent's id to apply the draft and create an immutable version. `save_agent_version` compiles the already approved specification into the current version without applying unpublished edits. OAuth connections need both edit and publish consent for that tool. Both tools leave production environment promotion to its separate controls.
6. Run `run_agent_simulations` with chosen scenario keys and read `get_agent_simulation` until it finishes. The normal offline runner and its required local dependencies must be installed. Simulation results do not establish live-call proof.
7. Only after the normal telephony ownership and entitlement requirements are met, use `bind_phone_number` for an already owned number. Purchasing and releasing numbers are not MCP tools.

The new writes carry `readOnlyHint: false`, explicit effect metadata, and the same audit and usage accounting as the draft tools. Publishing is marked `org.sempera/publishes: true`. Live client interoperability, production database behavior and carrier ownership checks require separate authorized proof; local tests do not claim those.

## Build and test an agent from an outside AI client over REST

A client that does not speak MCP can do the same over the REST API, with a key an owner of the workspace creates in Settings, API keys. The steps below need `agents:write` to create and edit a draft and to try it with a typed preview, and `tests:write` to run the test battery. The key reads results back with the matching `read` scopes. A key made in the App holds every scope a developer key may have, so it can also publish (`agents:publish`) and place a real outbound phone call (`calls:write`). Keep it private and do not paste it into a shared chat.

| Step | Method and path | Scope |
| --- | --- | --- |
| Create a draft agent | `POST /v1/agents` with `{"name": "..."}` (optional `template`, `answers`) | `agents:write` |
| Read the draft and its revision | `GET /v1/agents/{agent_id}/draft` | `agents:read` |
| Edit the draft | `PATCH /v1/agents/{agent_id}/draft` with `{"fields": {...}, "expect_revision": "..."}` | `agents:write` |
| Add a test scenario to the draft | `POST /v2/agents/{agent_id}/scenarios` | `agents:write` |
| Try the draft with one typed message | `POST /v1/agents/{agent_id}/preview` with `{"message": "..."}`; it never places a call | `agents:write` |
| Run the test battery | `POST /v1/tests` with `{"agent_id": "...", "scenarios": ["..."]}`; it answers `202` and runs in the background | `tests:write` |
| Read a test run | `GET /v1/tests/{test_id}` (or the `get_test_run` MCP tool) | `tests:read` |

Send an `Authorization` header with the value `Bearer <api-key>`, replacing the placeholder with your key ([Authentication and credentials](/authentication)). A draft save that carries an old `expect_revision` is refused with `409 conflict`, so read the draft first and send its `revision`.

What a key cannot do:

- **Make another key.** Only an owner signed in to the App can, so a key cannot mint a narrower one.
- **Use the Builder.** The Builder's jobs (start, answer, review, apply) run inside the signed-in app. They are not on the API, and a key does not open them.

A connector that signs in with OAuth, such as a ChatGPT connector, uses the sign-in above. No real account has proven it yet ([Supported clients](/supported-clients)).

## Retained candidate checks

Read `get_agent_draft`, review its canonical fields and diff, then pass its revision as `candidate_revision` to `run_agent_tests`. Also pass exactly `runtime_policy: {"evidence":"local-model","tools":"fixture","max_cost":0}`. The two arguments are a pair: a missing policy or revision, a live tool policy, a hosted-model request, a nonzero cost limit or unknown policy fields is refused. The configured hosted fallback is not inherited. If the local model is unavailable, the run fails honestly rather than switching to a paid model.

The candidate response identifies the reviewed draft revision, the SHA-256 of the actual compiled candidate and its parent AgentVersion. Its runtime policy is explicit and `release_evidence` is false. Check results are written to the existing App Checks ledger, so `list_tests` and `get_test_run` can review them after a process restart. This does not create a new builder, agent store, compiler or publication road. These retained runs need Sempera's persistent evidence store; a deployment without it is refused before a battery starts. The actual served model build still needs independent runtime evidence; the policy label is not proof of a model version or a quality pass.

Fixture batteries in automated tests prove the route, compiler, private tool facade, candidate binding, record retention and refusal behavior. They are not local-model quality evidence, live-model evidence, private host receipt or a production approval. ChatGPT authorization remains unavailable until the separately approved external grant and release gates are satisfied.
